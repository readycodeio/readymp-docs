# Installation

The OblivionMP server is distributed as a binary package, for Windows and Linux.

## Requirements

The server binary itself is self-contained, but [server-side mods](mod-management) run on CoreCLR, which the server starts at launch. That means the [**.NET 10 runtime**](https://dotnet.microsoft.com/download/dotnet/10.0) has to be installed on the machine, even if you do not intend to install any mods of your own. The `dotnet-runtime-10.0` package is enough, you do not need the SDK.

<Tabs groupId="os">
<TabItem value="windows" label="Windows">

The [official installer](https://dotnet.microsoft.com/download/dotnet/10.0) puts the runtime where the server expects it, so there is nothing else to do.

</TabItem>
<TabItem value="linux" label="Linux">

Install it with your package manager, or with Microsoft's [install script](https://learn.microsoft.com/dotnet/core/install/linux-scripted-manual#scripted-install). The server looks for the runtime in the usual locations, in this order:

1. `/usr/lib/dotnet` (Debian and Ubuntu packages)
2. `/usr/lib64/dotnet` (Fedora and RHEL)
3. `/usr/share/dotnet` (Microsoft packages and the install script)
4. `~/.dotnet`

A directory only counts if it actually contains `host/fxr`, so a leftover from an uninstalled version does not get in the way. If your runtime lives somewhere else, point `DOTNET_ROOT` at it:

```shell
DOTNET_ROOT=/opt/dotnet ./server
```

Check where yours is with `dotnet --info | grep 'Base Path'`.

</TabItem>
</Tabs>

:::note

If the runtime is missing, the server exits at startup with `Cannot locate a .NET installation containing host/fxr` and lists the directories it checked.

:::

## Installation

Extract the binary package to a location of your choice.

After extraction, the directory structure should look like this:

<Tabs groupId="os">
<TabItem value="windows" label="Windows">

```text
server/
├── server.exe                        # Main server binary
├── config.json                       # Configuration file
├── e_sqlite3.dll                     # Dependency
├── aspnetcorev2_inprocess.dll        # Dependency
├── *.dll                             # Managed runtime dependencies
├── modloader/                        # The client mod loader, handed out to connecting players
├── mods/                             # Installed mods, one folder each
|   ├── OblivionMp.Sdk/               # SDK mod
|   |   ├── manifest.json             # Mod manifest, shared by both halves
|   |   ├── client/                   # Handed out to connecting players
|   |   └── server/                   # Stays on the server
|   ├── OblivionMP.Chat/              # Chat
|   ├── OblivionMp.MarkerMod/         # Name tags over other players
|   ├── OblivionMp.Quests/            # Quests
|   └── OblivionMp.SeedLoader/        # Fills a fresh world with the game's furniture, containers and items
├── saves/                            # Directory for game saves (empty by default)
└── wwwroot/                          # Admin panel assets
```

## Configuration

You can adjust server settings by editing the `config.json` file. In the following table, the `:` notation is used to represent nested settings.

| Setting | Type | Default | Purpose |
| --- | --- | --- | --- |
| `Server:Port` | number | `9050` | The port on which the server listens for incoming connections |
| `Server:Password` | string | empty | Optional. When set, players must enter this password in the Launcher to join. Leave empty or omit for an open server. |
| `Telemetry:OptOut` | boolean | `false` | Set to `true` to opt out of sending anonymous telemetry to ReadyM. Defaults to `false`. |
| `ServerList:Enabled` | boolean | `false` | Whether to list the server on the public server list in the Launcher. |
| `ServerList:Name` | string | empty | The server's name in the Launcher. Maximum 50 characters. |
| `ServerList:Gamemode` | string | empty | Game mode tag, shown next to the name. Maximum 15 characters. |
| `ServerList:MaxPlayers` | number | `64` | Maximum number of players, between 1 and 65535. Enforced when players connect. |
| `ServerList:PublicHost` | string | `null` | The public IP address or hostname players connect to. Required for the server to be listed. |
| `ServerList:PublicPort` | number | `null` | The public port players connect to. Required for the server to be listed. Can differ from `Server:Port`, for example behind a port forward. |
| `ServerList:Description` | string | empty | Optional. Short plain-text description, shown in the server's Join panel when it has no [server card](branding#server-card). Maximum 300 characters. |
| `ServerList:Country` | string | empty | Optional. Two-letter ISO 3166-1 alpha-2 country code, such as `PL` or `US`, used to show a flag. |
| `ServerList:LicenseKey` | string | empty | Optional. License key that gives the server the **Verified** badge. See [Verified status](publishing-your-server#verified-status). |
| `Save:RootPath` | string | `saves` | The folder the world and player saves are written to. A relative path is relative to the server folder. |
| `Save:Format` | string | `Json` | The format of the save data. `Json` is the only format this release accepts. |
| `Save:Compression` | string | `Fastest` | How hard the save files are compressed: `Fastest`, `Optimal`, `SmallestSize` or `NoCompression`. Smaller files take longer to write. |
| `Save:AutosaveInterval` | duration | `00:05:00` | How often the server saves the world and the players, as `hh:mm:ss`. `00:00:00` turns autosave off, and the server then saves only when it shuts down. |
| `Save:ShutdownDrainTimeout` | duration | `00:00:30` | How long the server waits at shutdown for saves still in progress to finish writing, as `hh:mm:ss`. Saves that have not finished by then may be lost. |
| `Save:SegmentBackups` | boolean | `false` | Set to `true` to keep a `.bak` copy of the previous version of each area and cell save file as well. The world's global save file keeps one either way. |

:::note

`Server:Password` gates every player, including admins and whitelisted users. Password-protected servers are shown with a lock on the public server list.

:::

The `ServerList` settings only matter when `ServerList:Enabled` is `true`. Their limits and how the server checks them are described in [Publishing your server](publishing-your-server).

An unknown `Save:Format` or `Save:Compression` value stops the server at startup, with `Failed to convert configuration value` in its console output. Changes to `config.json` take effect when the server is restarted.

The OblivionMP server runs on the same binaries as [WukongMP](/wukong-mp/docs/what-is-wukong-mp), so the hosting features are identical: the same [admin panel](admin-panel) and the same public [server listing](publishing-your-server).

## First launch

Start the server by running the `server.exe` binary.

On first launch, the server creates a `data/` directory inside the server folder. 
This directory contains the `web.db` database file, where persistent data is stored.

Unless changed in `config.json`, the server listens on one port, 9050, over both protocols:

| Port | Protocol | Purpose |
| --- | --- | --- |
| 9050 | TCP | Joining and mod sync over HTTP, and the [admin panel](admin-panel) |
| 9050 | UDP | Game traffic: player connections, game state synchronization and the rest |

:::important[Forward TCP and UDP]

Joining starts over HTTP. The launcher asks the server for a connection ticket and for the mod manifest, and the game
connects over UDP after that. So **TCP and UDP both have to reach the server on the game port**, and if you remap the
port on the way in, remap it the same way for both. A port forward or tunnel that carries UDP alone ends in
[Server did not respond](#server-did-not-respond).

:::

Opening TCP also puts the [admin panel](admin-panel) on the public address, at `http://<your-server>:9050`, where it
answers the same way it does at `http://localhost:9050`. It asks anyone who opens it for the setup PIN the server
prints on its first launch, and then for a ReadyM sign-in.

## Troubleshooting

### Server did not respond

The launcher shows this when its first request to your server, the HTTP one, goes unanswered. The game has not tried
UDP yet at that point, so the usual cause is that the request never reached the server.

The admin panel being up proves only that the server is running on that machine, not that a player can reach it.

- **Forward both protocols.** Check the router's rule covers TCP as well as UDP, and that both point at the machine
  running the server.
- **Check the firewall on the server's own machine**, not only the router. Windows asks once, when the server first
  binds the port, and a prompt that was dismissed leaves inbound traffic blocked.
- **Tunnels and VPNs have to carry both protocols.** A TCP-only tunnel cannot pass game traffic, and a UDP-only one
  cannot pass the join. Use a tunnel that forwards TCP and UDP together on one port. Or put your
  players on the same virtual network, with something like Tailscale or ZeroTier, and have them join the address the
  server has on that network.
- **Carrier-grade NAT.** If your router's WAN address is in `100.64.0.0/10`, your connection is shared with other
  subscribers, and the address a player would connect to belongs to your ISP rather than to you, so a port forward on
  your own router changes nothing. A tunnel or a virtual network is the way around it.
- **Joining your own server from inside your own network.** Some routers do not loop a connection on the public
  address back to a machine on the LAN, which is called NAT hairpinning. Use the server's local address from home, and
  the public one from outside.
- **Check the address you advertise.** What goes on the public list is not checked against what the server binds, so
  a stale or mistyped entry there sends players somewhere that does not answer: see
  [Publishing your server](publishing-your-server#network-configuration).
