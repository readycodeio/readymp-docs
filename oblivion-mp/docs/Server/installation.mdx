# Installation

The OblivionMP server is distributed as a binary package, for Windows and Linux.

:::info[1.1.0]

**1.1.0** ships with SDK 1.1.0, which adds [networked events](../Modding/Concepts/networked-events.md) and drops old APIs, so mods built for 1.0.0 need rebuilding against it. OblivionMP is still a work in progress, so expect rough edges, and report them on [Discord](https://discord.gg/obmp).

:::

## Requirements

The server binary itself is self-contained, but [server-side mods](mod-management) run on CoreCLR, which the server starts at launch. That means the [**.NET 10 runtime**](https://dotnet.microsoft.com/download/dotnet/10.0) has to be installed on the machine, even if you do not intend to install any mods of your own. The `dotnet-runtime-10.0` package is enough, you do not need the SDK.

<Tabs groupId="os">
<TabItem value="windows" label="Windows">

The [official installer](https://dotnet.microsoft.com/download/dotnet/10.0) puts the runtime where the server expects it, so there is nothing else to do.

</TabItem>
<TabItem value="linux" label="Linux">

Install it with your package manager, or with Microsoft's [install script](https://learn.microsoft.com/dotnet/core/install/linux-scripted-manual#scripted-install). The server looks for the runtime in the usual locations, in this order:

1. `/usr/lib/dotnet` (Debian and Ubuntu packages)
2. `/usr/lib64/dotnet` (Fedora and RHEL)
3. `/usr/share/dotnet` (Microsoft packages and the install script)
4. `~/.dotnet`

A directory only counts if it actually contains `host/fxr`, so a leftover from an uninstalled version does not get in the way. If your runtime lives somewhere else, point `DOTNET_ROOT` at it:

```shell
DOTNET_ROOT=/opt/dotnet ./server
```

Check where yours is with `dotnet --info | grep 'Base Path'`.

</TabItem>
</Tabs>

:::note

If the runtime is missing, the server exits at startup with `Cannot locate a .NET installation containing host/fxr` and lists the directories it checked.

:::

## Installation

Extract the binary package to a location of your choice.

After extraction, the directory structure should look like this:

<TabItem value="windows" label="Windows">

```text
server/
├── server.exe                        # Main server binary
├── config.json                       # Configuration file
├── e_sqlite3.dll                     # Dependency
├── aspnetcorev2_inprocess.dll        # Dependency
├── *.dll                             # Managed runtime dependencies
├── modloader/                        # The client mod loader, handed out to connecting players
├── mods/                             # Installed mods, one folder each
|   ├── OblivionMp.Sdk/               # SDK mod
|   |   ├── manifest.json             # Mod manifest, shared by both halves
|   |   ├── client/                   # Handed out to connecting players
|   |   └── server/                   # Stays on the server
|   ├── OblivionMP.Chat/              # Chat
|   ├── OblivionMp.MarkerMod/         # Name tags over other players
|   ├── OblivionMp.Quests/            # Quests
|   └── OblivionMp.SeedLoader/        # Fills a fresh world with the game's furniture, containers and items
├── saves/                            # Directory for game saves (empty by default)
└── wwwroot/                          # Admin panel assets
```

## Configuration

You can adjust server settings by editing the `config.json` file. In the following table, the `:` notation is used to represent nested settings.

| Setting | Type | Purpose |
| --- | --- | --- |
| `Server:Port` | number | The port on which the server listens for incoming connections |
| `Server:Password` | string | Optional. When set, players must enter this password in the Launcher to join. Leave empty or omit for an open server. |
| `Telemetry:OptOut` | boolean | Set to `true` to opt out of sending anonymous telemetry to ReadyM. Defaults to `false`. |

:::note

`Server:Password` gates every player, including admins and whitelisted users. Password-protected servers are shown with a lock on the public server list.

:::

The OblivionMP server runs on the same binaries as [WukongMP](/wukong-mp/docs/what-is-wukong-mp), so the hosting features are identical: the same [admin panel](admin-panel) and the same public [server listing](publishing-your-server).

## First launch

Start the server by running the `server.exe` binary.

On first launch, the server creates a `data/` directory inside the server folder. 
This directory contains the `web.db` database file, where persistent data is stored.

Unless changed in `config.json`, the server listens on one port, 9050, over both protocols:

| Port | Protocol | Purpose |
| --- | --- | --- |
| 9050 | TCP | Joining and mod sync over HTTP, and the [admin panel](admin-panel) |
| 9050 | UDP | Game traffic: player connections, game state synchronization and the rest |

:::important[A server other people join needs both]

Joining starts over HTTP. The launcher asks the server for a connection ticket and for the mod manifest, and only once
it has them does the game connect over UDP. So **TCP and UDP both have to reach the server on the game port**, and if
you remap the port on the way in, remap it the same way for both. A port forward or tunnel that carries UDP alone ends
in [Server did not respond](#server-did-not-respond).

:::

Opening TCP also makes the admin panel reachable at that address. It sits behind the setup PIN and a ReadyM sign-in, so
it is not open to anyone who finds it, but it is no longer only yours to see.

## Troubleshooting

### Server did not respond

The launcher shows this when its first request to your server, the HTTP one, goes unanswered. The game has not tried
UDP yet at that point, so the cause is almost always that nothing outside your network can reach the server, rather
than anything the server itself did.

The admin panel being up proves only that the server is running on that machine. It says nothing about whether a player
can reach it.

- **Forward both protocols.** The game port needs TCP and UDP pointed at the machine running the server. A rule for UDP
  alone fails here every time, and it is the single most common cause.
- **Check the firewall on the server's own machine**, not only the router. Windows asks once, when the server first
  binds the port, and a prompt that was dismissed leaves inbound traffic blocked.
- **Tunnels and VPNs have to carry both protocols.** A TCP-only tunnel cannot pass game traffic and a UDP-only one
  cannot pass the join, so use a tunnel that forwards TCP and UDP together on one port, or put your players on the same
  virtual network with something like Tailscale or ZeroTier and have them join the address the server has on it.
- **Carrier-grade NAT.** If your router's WAN address is in `100.64.0.0/10`, your connection is shared with other
  subscribers and no port forward can work, because nothing of yours is reachable from outside. A tunnel or a virtual
  network is the way around it.
- **Joining your own server from inside your own network.** Some routers refuse to loop a connection on the public
  address back to a machine on the LAN. Use the server's local address from home, and the public one from outside.
- **Join the address the server actually listens on.** What you advertise on the public list is not checked against
  what the server binds: see [Publishing your server](publishing-your-server#network-configuration).
